## MVP success criteria (set by the user, 2026-10-23)

The MVP is done when each of these is shown working:

1. The plugin works from all three Antigravity surfaces: the `agy` CLI, the desktop app and the IDE (#30). The MVP closes on the `agy` CLI and the desktop app; the IDE waits on Google (see Decisions).
2. On every supported surface, if the Databricks CLI profile isn't configured, the agent asks the user for their workspace details (#33).
3. It uses those details to set up the Databricks CLI profile (#33).

Until then, everything else waits. The non-Genie work was closed as not planned on 2026-10-23 (see Status).

## What we know

**Antigravity plugins (the guide, corrected against the shipped app in #2 and #34)**

- A plugin is a `plugin.json` plus any of: `skills/<name>/SKILL.md`, `mcp_config.json`, `agents/<name>.md`, `rules/`, `hooks.json`, `README.md`, `assets/`.
- The manifest sits at the root, or at `.antigravity-plugin/plugin.json` when the repo also ships `.claude-plugin/` or `.cursor-plugin/` manifests. Component paths always resolve from the plugin root.
- `name` is kebab-case, must match the folder, and prefixes MCP server names (`<plugin>-<server>`). The shipped loader (checked on 2.24.0 in #2, and on 2.25.0 against the app's own plugin docs in #34) reads only `name`, `description`, `displayName`, `logo`, `suggestedPrompts` (up to 3), `version`, `disabled` and `skills`. It silently drops `author`, `homepage` and the other metadata the guide asks for.
- The manifest ships `author` and `license` anyway, because the guide requires or recommends them and `agy plugin validate --strict` accepts them (it also accepts `homepage`, `keywords` and `repository`, which we haven't added). It leaves out `category` and `tags`: the guide recommends them, but `--strict` flags each as an `unknown field ... is ignored` warning, and the tests and CI run `--strict`, so adding them would fail the build (#34). The guide wants a higher `version` for every published update, and the app doesn't enforce that, so a test does, and it is stricter, as the project's rule is: a change under `plugins/databricks-genie/` passes only if the version keeps the merge-base's major and minor and has a higher last number (a plugin that `main` doesn't have yet can start at any version). See the working rules.
- `logo` is a bundled .png, .svg, .jpg, .jpeg or .webp file, or an https URL on a Google domain only; the guide allows any https URL. The guide wants it square, at least 128x128, with transparent padding. We ship `assets/logo.png`, the Databricks icon at 768x768 with an alpha channel, and a test reads its PNG header (#34).
- MCP servers are remote (`serverUrl` + `headers`) or local (`command`/`args`/`env`). The guide says Node ships with the app, but plugin servers don't get it: with Node off PATH, a Node server never starts. That's why the Genie bridge is Python.
- `variables` (`name`, `title`, `description`, `link`) are asked for at install and stored as plain text in `~/.gemini/config/config.json`. The guide's `secret`/keychain option doesn't exist in 2.24.0. A server that declares `variables` stays off until the user fills them in through the app, so the Genie plugin declares none (#21).
- Plugin MCP servers register as `<plugin>_<server>` (here `databricks-genie_genie`). Their tools load lazily and are called through `call_mcp_tool`. Headless `agy -p` runs need allow rules such as `mcp(databricks-genie_genie/genie_ask)` in `~/.gemini/antigravity-cli/settings.json`.
- Antigravity cuts each MCP tool call off at 3 minutes ("timed out after 3m0s"), so the bridge's wait has to end sooner (#28). An undocumented per-server `timeoutSeconds` field, seen in the `agy` and language-server binaries and in a public bug report on google-antigravity's CLI, may raise that limit. It's untested for plugin servers.
- `oauth` is `{clientId, clientSecret}`, or automatic discovery with dynamic client registration when it's left out. There's no field for scopes.
- The installed copy is read-only at `~/.gemini/config/plugins/<name>`. Use `${PLUGIN_ROOT}`, `${PLUGIN_DATA}` and `${VAR}`, never absolute paths.
- Skill frontmatter: `name` (matches the folder, becomes `/name` in chat) and `description` (what it does and when to use it).
- Subagent frontmatter (antigravity.google/docs/subagents): `name` and `description` (both required), `tools`, `mcpServers`, `commandExecutionPolicy` (off|auto|eager|sandbox), `model` (inherit|flash|pro), `mainAgent`, `subagent`, and `skills`/`plugins`. The guide's `enable_*` keys don't appear in Google's docs, so don't use them.
- Rules: `rules/AGENTS.md` is always on. `rules/<rule>.md` takes a `trigger` of always_on, model_decision, glob or manual.
- Hooks: PreToolUse, PostToolUse, PreInvocation, PostInvocation and Stop. JSON comes in on stdin and goes out on stdout.
- Managing plugins: in the app, Customizations → Plugins (Discover, Installed) installs by Marketplace ID, and there's no Install from URL (2.25.0's UI bundle has none either). Git URLs and local folders go through `agy plugin install <url|path>` (the CLI is a separate download), then a restart. `/plugin` works in chat.
- Install from a URL (#36): `agy plugin install https://github.com/datasciencemonkey/antigravity-bricks-plugin` works with no layout change. `agy` clones the repo with `git` and treats its `plugins/` folder as a bulk plugins directory, installing each child that has a manifest. It takes only github.com HTTPS URLs (and `/tree/<branch>/<dir>` forms), takes no flags, and reinstalls in place when run again. A root manifest would copy the whole repo into the install, and `agy plugin install` doesn't read `marketplace.json`, so the layout stays as it is. The install test runs `agy plugin install <repo root>` with HOME set to a fresh temporary folder, so it never touches the real `~/.gemini`.

**From research (#2, #3, #4)**

- Databricks isn't in Antigravity's MCP Store or Marketplace. Discover is curated by Google and fed by `marketplace.json` catalogs; there's no submission process. Plugins ship today as GitHub repos installed with `agy plugin install <url>`.
- Global skills now live in `~/.gemini/config/skills/`. The Databricks CLI still writes to `~/.gemini/antigravity/global_skills`, which Antigravity 2.24 doesn't read (confirmed in #25), so skills it installs don't show up. Our plugin ships its own skill and doesn't depend on those.
- The app's UI includes MCP Apps support, so Genie One's interactive view may render (untested). `agy -p "<prompt>" --output-format stream-json` runs a prompt without the UI, which can script the demo.
- Repos carrying several manifests are normal. Skills must sit one folder deep, `hooks.json` must use Antigravity's own format, and `rules/` is shared with Cursor.
- `databricks/databricks-agent-skills` builds Claude, Codex, Copilot and Cursor bundles from one source, but has no Antigravity target yet. It ships no MCP servers. Its root URL doesn't install with `agy plugin install` ("could not detect plugin structure"). Its Claude bundle does install, from `https://github.com/databricks/databricks-agent-skills/tree/main/plugins/databricks/claude` or a local path, giving 34 skills and no MCP. `agy plugin validate --strict` rejects its Claude and Cursor bundles because they have no native `plugin.json` (#25).
- Genie One MCP is GA at `https://<workspace>/ai-gateway/mcp-services/system.ai.genie_one_mcp` (scope `ai-gateway`). Its tools are `genie_ask`, `genie_poll_response`, `genie_get_query_result`, `genie_cancel_response` and `view_ask`. The older `/api/2.0/mcp/genie` turns off on 2026-10-31. The per-space `/api/2.0/mcp/genie/{space_id}` (scope `genie`) stays.
- Sign-in: Databricks has no dynamic client registration, so Antigravity's automatic OAuth can't connect on its own. Direct OAuth needs an admin-registered OAuth app. PATs work, but would sit in plain text in `config.json`. A local bridge that gets fresh tokens from `databricks auth token` works with no admin step; Databricks' `ug mcp-proxy` does this in Python too.
- The Genie skills (`databricks-data-discovery`, `databricks-genie-agents`) drive Genie through the CLI (`databricks genie ask`, which CLI v1.22.1 has), not through MCP. They should work unchanged in Antigravity if `databricks-core` is installed alongside them and the CLI is logged in. We don't bundle them (see Decisions). They're under the Databricks License, which allows redistribution with the license included and changes marked.
- Antigravity is three products: the desktop app (2.25.0, which holds the plugin engine), the IDE (2.5.5, VS Code-style, Open VSX), and the `agy` CLI (`curl -fsSL https://antigravity.google/cli/install.sh | bash`). Plugins apply to the CLI and the desktop app. The IDE doesn't run plugin MCP servers yet (#30), and turning a plugin on or off there rewrites its manifest.

**The Databricks CLI (v1.22.1, checked against the real CLI in #33)**

- `databricks auth profiles --skip-validate` exits 1 when the config file is missing (`cannot parse config file: no configuration file found at <path>`), and a new machine has none. It exits 1 too when the path is a folder, and prints `{"profiles": null}` for an empty file. On Windows the CLI looks under USERPROFILE for its config, wherever HOME points. `auth token` fails fast, with no network call, for a profile that isn't listed or doesn't sign in with U2M.
- `DATABRICKS_AUTH_STORAGE` (`plaintext` or `secure`) chooses where `auth login` and `auth token` keep U2M tokens, in the file cache or the OS keyring, and overrides `[__settings__] auth_storage`. The CLI's own errors tell users to set it (`DATABRICKS_AUTH_STORAGE=plaintext` keeps the file cache), so a headless machine without a keyring depends on it. `DATABRICKS_OAUTH_CALLBACK_PORT` and `DATABRICKS_DISABLE_OAUTH_REFRESH_TOKEN` also shape a sign-in. The CLI has to see all three, which is why the bridge leaves its environment alone.
- It lists only config sections that have a host or an account_id; a section with only an `account_id` is listed with no host. A section with neither, such as an Azure service principal that sets `azure_workspace_resource_id`, or an empty header, is in the file and not in the list.
- The INI parser (go-ini) puts keys before the first header into DEFAULT, and merges them with a later `[DEFAULT]` header. A key ends at the first `=` or `:`. A comment after a header's `]` is ignored, a section's name keeps its spaces, and a key line with no delimiter makes `auth profiles` fail.
- `databricks configure --host <host> --profile <name>` (it wants an https host, and reads the token from stdin when it isn't interactive) writes a comment, an empty `[DEFAULT]` header, the profile, and a `[__settings__]` section with `default_profile`. `auth profiles` lists only the profile.
- The tests keep a stand-in `databricks` CLI honest: it reads the config file the same way, and the same tests run against the real CLI when it's installed, with a temporary folder as HOME and `DATABRICKS_CONFIG_FILE` in it, so neither reads the real `~/.databrickscfg`.

## Decisions

- First user (#5): a developer at a Databricks customer standardized on Google's AI tools. They're building in Antigravity against governed data that their data team already serves through a Genie space. Their first question is a business metric the agent would otherwise guess at, e.g. "Top 10 products by revenue last quarter vs. the prior quarter?", then "By region?", with Genie's SQL going into their code. Business users are out of scope. This is the director's call; the user can override it.
- Sign-in (#8): a Python bridge inside the plugin (standard library only, Python 3.9+) gets a fresh token from `databricks auth token --profile` on each request and forwards calls to the Genie One MCP. The plugin has no settings: the bridge reads the workspace host from `databricks auth profiles` (a local read of the Databricks config file, no network call), for the `DEFAULT` profile or the one `DATABRICKS_CONFIG_PROFILE` names. Only the plugin's own skill (`antigravity-databricks-genie`) ships, and it includes a CLI fallback (`databricks genie ask`); an always-on rule says to prefer the MCP tools. Build the skills first, then the bridge; demo the bridge. No PATs in settings. Admin-registered OAuth is documented, not built. On 2026-10-21 the user confirmed it stays CLI-brokered U2M OAuth (`databricks auth login`).

- Demo setup (#10, decided by the user): the `DEFAULT` CLI profile (a serverless demo workspace), with a new Genie space to be created over its sample data. Installing `agy` and running the spike (#21) are approved.
- Standalone connector (#25, #26, decided by the user on 2026-10-22): the plugin is a standalone way to connect Antigravity to Databricks Genie. It doesn't assume other Databricks skills are installed, and it doesn't bundle Databricks' published skills. There's no upstream work in `databricks/databricks-agent-skills`. The skill is renamed `antigravity-databricks-genie`, so its slash command is `/antigravity-databricks-genie`; the MCP server key stays `genie` (`databricks-genie_genie`). The bridge waits up to 150 s for Genie, so it gives up before Antigravity's 3-minute per-call limit (#28). That was plugin version 0.2.1. Genie keeps working on a question after the bridge gives up, and a timed-out `genie_ask` loses its IDs, so the timeout error and the skill say that asking again starts a duplicate question; for a follow-up they say to call `genie_cancel_response` with its `conversation_id` first, and a timed-out `genie_poll_response` gets its IDs back for polling. Fetching a result or cancelling starts no question, so a timeout there just says to try again, and a timeout while connecting says the request wasn't sent, so it warns of no duplicate.
- Start with Antigravity (the user, 2026-10-22): other IDE targets, such as one repo for Claude Code, Cursor and Antigravity (#13), are out of scope. #13 was closed as not planned on 2026-10-23.
- MVP (the user, 2026-10-23): the MVP success criteria above are the definition of done. The POV, scope and other non-Genie work were closed as not planned on 2026-10-23.
- MVP scope (the user, 2026-10-23): the MVP closes on the `agy` CLI and the desktop app, and the IDE waits on Google (#30). IDE 2.5.5 doesn't run plugin MCP servers, and turning the plugin on or off there rewrites its manifest, so the plugin can't work there until Google changes that. Everything else in the plugin is the same on the surfaces that do run it.
- Sign-in paths (the user, 2026-10-23): U2M through the Databricks CLI is the default. Service principal (OAuth M2M) sign-in comes after the MVP as a secondary, opt-in path, via env-provided client credentials, together with the live CI test (#39).
- Guide review (#34, 2026-10-23): where the guide and the shipped app disagree, the plugin follows the app. It ships `author` and `license`, which the guide requires or recommends and the validator accepts, but not `category` or `tags`, which `--strict` rejects as unknown fields. It declares no `variables` or `secret` (the app ignores top-level `variables`, and per-server ones keep the server off until the user fills them in, as plain text), names its server `databricks-genie_genie` (the app joins plugin and server with an underscore, the guide says a hyphen), runs Python instead of Node (plugin servers don't get the app's Node), has no `mcpServers` path in the manifest (the app ignores it and reads `mcp_config.json`), and bundles its logo (the app accepts an https logo only on a Google domain). It ships no hooks, glob rules or subagents; if it adds them, they follow the app's formats, not the guide's. Every change to the plugin ships under a higher version, which a test enforces, and the plugin carries its own MIT license file, because an install copies only its folder. The plugin is now version 0.3.2.
- First-use setup (#33, the director's design, 2026-10-23): setup goes through the Databricks CLI. The bridge answers `initialize` and `tools/list` itself, so its tools show up before any CLI profile exists. `genie_connection` reports the status, the profile and the host the bridge will call, and `genie_setup` sets up the profile with `databricks auth login` in the background, never pointing an existing profile at another workspace. The CLI config is the only state, so every surface that runs the plugin behaves the same (the IDE waits on Google, #30). MCP elicitation isn't used: Antigravity's handlers for it are undocumented, and headless `agy -p` runs can't answer it. When the CLI is missing, the agent offers Databricks' official installer and runs it only after the user approves, explaining that the CLI is the safest way to run OAuth U2M sign-in from a local machine (the user's call). The bridge reads the workspace host from `databricks auth profiles`, a local read, instead of `auth describe`. A missing config file means no profiles: `auth profiles` exits 1 when there is no file, and a new machine has none. The bridge asks the CLI first and takes its failure for no profiles only when the config file is missing where the bridge looks too, because the CLI can keep its config somewhere else (on Windows it uses USERPROFILE, not HOME, and the bridge's own guess does the same). Then the bridge reports `not_configured` and `genie_setup` goes ahead (`auth login` creates the file). `genie_setup` signs a profile in again only if its auth type is `databricks-cli` (U2M). It never touches a profile with another auth type, because `auth login` would rewrite it and drop its token or client secret; it reports `unsupported_auth` instead. The same goes for a profile the CLI hides: `databricks auth profiles` (CLI v1.22.1) lists only config sections that have a host or an account_id, so an Azure service principal that sets `azure_workspace_resource_id` looks like no profile at all. Before `genie_setup` signs a profile in, the bridge reads the key names of each section in the Databricks config file (`DATABRICKS_CONFIG_FILE`, else `~/.databrickscfg`; never a value), and a section with the profile's name that has at least one key makes `genie_connection` report `profile_exists_unreadable` and `genie_setup` refuse, with a next step to use a separate profile. Keys before the first header count as DEFAULT's, because the CLI's INI parser (go-ini) puts them there. A header with no keys doesn't count: `databricks configure` writes an empty `[DEFAULT]` header into a new config, and signing in over it loses nothing, whereas refusing it would break first use for anyone with a named profile. A config file the bridge can't read counts as holding keys. The workspace comes only from the profile: the bridge reads no workspace from the environment, so an inherited `DATABRICKS_HOST` doesn't steer where it calls, and it leaves the CLI's environment alone (see the next decision). `GENIE_MCP_URL`, a hook for the tests' stand-in Genie server, is accepted only for a loopback URL. A background sign-in is recorded in `~/.cache/antigravity-databricks-genie/`, with no token, so the bridge that `agy -p` starts for the next turn still sees it. That folder is made with mode 0700 and checked for being the user's own and not a link; the record in it is 0600 and written atomically. The shared temp folder isn't used. Plugin version 0.3.0 added this setup, and 0.3.1 adds the safeguards above (the hidden-section check, the missing-config handling, the rule that the profile's host decides, and the timeout errors) and the private folder.
- The CLI owns its environment (the user, 2026-10-23): the bridge leaves the CLI's environment alone; the CLI owns its config and environment variables. Its calls get the bridge's environment unchanged, as in the user's terminal, so `DATABRICKS_AUTH_STORAGE` (where the CLI keeps its U2M tokens), `DATABRICKS_OAUTH_CALLBACK_PORT` and the rest reach it. The bridge itself reads only `DATABRICKS_CONFIG_PROFILE` (the profile's name) and `DATABRICKS_CONFIG_FILE` (for the hidden-section check), plus `DATABRICKS_CLI`, the CLI's path, which the tests use; it never reads `DATABRICKS_HOST`, and the host it calls comes only from the CLI's profile listing. A test keeps it that way. The price is that an exported `DATABRICKS_HOST` or `DATABRICKS_TOKEN` for another workspace can make the CLI report a sign-in error, so the READMEs tell users to unset them. `GENIE_MCP_URL`, our own hook for the tests' stand-in Genie server, is accepted only for a loopback URL. An earlier version filtered the CLI's environment and dropped every `DATABRICKS_*` variable but two. That hid `DATABRICKS_AUTH_STORAGE`, which in v1.22.1 chooses where U2M tokens live (a plaintext file or the OS keyring) and overrides `[__settings__] auth_storage`, so a headless sign-in made with plaintext storage looked like `login_needed`.

## Open questions

- The bridge ignores the Databricks CLI's `[__settings__] default_profile` setting, the profile the CLI uses when none is named, which `databricks configure` writes (v1.22.1). The bridge uses `DEFAULT` unless `DATABRICKS_CONFIG_PROFILE` says otherwise, and never picks a profile for the user. Whether to honor `default_profile` is open.
- New questions go to the director first.

## Working rules

- Questions and dispatch plans go to the `director` subagent first. It's a local dev-loop helper, defined in a git-ignored `.claude/agents/director.md` and not shipped in the repo. It runs distinct to-dos in parallel and sequences the rest, investigates questions with its tools, and says when only the user can decide. Consult it before dispatching any other subagent.
- Every to-do and idea is an issue on the board, assigned to `datasciencemonkey`; move it Todo → In Progress → Done as work happens, and never close one without that assignee. Local helper: `uv run python .omc/scripts/board.py move <issue> "<status>"`.
- Use `uv` to run anything. Every commit is authored and committed as datasciencemonkey@gmail.com.
- Build everything test-first: write a failing test, watch it fail, then write the code. `uv run --locked pytest` is the one test command. It also scans for internal-only references, secrets, real workspace hostnames and wrong commit identities.
- Tests gate every push. Install the pre-push hook once per clone with `uv run python -m tools.install_hooks`. Run the suite before pushing; GitHub Actions runs it again on every push.
- **PRs.** Each issue merges through a PR. Its description has these parts, in order: `## Summary` (user-facing bullets of what changed), `## Issues` (`Closes #N`), `## Testing`, then the line "This pull request and its description were written by Isaac." Check it with `tools.repo_checks --stdin`. Merge by fast-forwarding `main` (`git push origin <head>:main`) after the tests and CI pass. GitHub marks the PR merged, and it closes the issue. Never use GitHub's merge buttons, which make GitHub the committer. The release workflow builds each release's notes from the Summary sections of the PRs merged since the previous tag.
- **Versions:** each change to the plugin bumps only the last number of `plugin.json`'s version (0.3.0 → 0.3.1 → 0.3.2). A release workflow tags `v<version>` and makes a GitHub Release when that commit passes CI on `main`. It never bumps anything itself. A test fails when a file under `plugins/databricks-genie/` differs from the merge-base with `origin/main` and the version isn't higher, and the bridge's `VERSION` has to match `plugin.json`.
- Check PR and issue text before posting: `uv run python -m tools.repo_checks --stdin < text.md`.
- Never relock dependencies through the internal package proxy (the hostname check will flag it). Relock somewhere public PyPI is reachable.
- Never choose a Databricks CLI profile yourself; ask the user. Never print tokens.
- Never print the contents of config or credential files: `~/.gemini/**`, an app's `settings.json`, `~/.databrickscfg`, `~/.databricks/*` and token caches. Print key names or hashes only. Say so in every subagent prompt.
- Don't change the user's Antigravity setup (`~/.gemini`, `~/.antigravity`) without asking.
- The repo is public (since 2026-10-20). Research notes are kept in `.omc/research/`, which is git-ignored. Internal-only Databricks material (from Glean or Slack) stays there. Keep it, and customer names, out of GitHub issues, PRs and committed files.
- Organization-specific patterns and customer names go in a local deny-list that is never committed: `.omc/denylist.txt` (git-ignored), or the file named by `REPO_CHECKS_DENYLIST`. It holds one regular expression per line. The repo checks and the test suite read it; where there is none, as in CI and fresh clones, those checks are skipped with a warning, so keep committed files free of internal names yourself.
- POV drafts live in `.omc/pov/` (git-ignored). The final version goes into a Google Doc in the user's Databricks Drive after review. GitHub only gets material from public sources.
- Base branches and PRs on `origin/main`. The main checkout's local `main` (7a072aa) is an unrelated empty commit.
- Update this file when research lands or a decision is made.
